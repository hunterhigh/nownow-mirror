# 定制版开发流程 v0.1

状态：流程已建立；个人优先的首版范围已确认，执行顺序见 `guanfu-master-development-plan.md`。数据模型、隔离环境与发布仍需在对应节点单独确认。

## 目标与原则

需求来源见 [产品简报](../../docs/product-brief.md)。在现有镜像上围绕 UI、个人任务与小团队效率持续迭代，保留可追溯的讨论和验收记录。

- 一轮讨论解决一个关键分歧，结论归档；候选想法不自动进入开发。
- 先验证使用路径与交互，再对需要的数据模型作决定。
- 每个开发切片能独立演示、验证和撤回；不按“全部前端／全部后端”分批交付。
- 流程服务个人／小团队：用少量文档和简短任务卡，不预设复杂项目管理平台。

## 阶段与通过条件

| 阶段 | 具体工作与产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 0. 本地基线 | 克隆镜像、隔离分支、检查依赖与测试，记录到 `docs/baseline.md` | 来源和提交可追溯；测试／lint／构建的通过、警告和未验证项分开记录 |
| 1. 场景探索 | 在 `docs/product-brief.md` 记录典型工作流、主要用户、设备和痛点 | 用户确认一个首要场景，以及如何判断它得到改善 |
| 2. MVP 定义 | 按场景列必做／延后／不做、最小操作闭环、任务与笔记关系、可见性；补入产品简报 | 每个必做项有可观察的验收条件，用户确认范围，未决问题不阻塞首个切片 |
| 3. UI 与交互 | 范围确认后新增 `docs/design.md`；先做低保真路径，再做关键界面和可交互原型 | 用户走通主路径；关键空态、失败态、窄屏和键盘操作有设计；确认视觉方向 |
| 4. 技术准备与切片 | 确认隔离开发环境和目标库；新增 `docs/backlog.md`，按需在本目录记录实施计划 | 环境与原项目隔离；首个切片达到 Ready；数据变化有权限／迁移／恢复方案 |
| 5. 迭代与体验验收 | 逐片实现、自动检查、浏览器验证、演示，再记录用户反馈 | 每片达到下述 Done；下一片根据反馈重排；不在一次迭代中暗增范围 |
| 6. 私有试用与发布 | 范围稳定后新增 `docs/releases.md`，记录版本、目标环境、已知限制、回滚／恢复步骤 | 用户确认发布目标并授权；预发布验收通过；备份／恢复及权限检查适用项通过 |

阶段 3 的样例数据原型可以在不连接数据库的前提下进行；真实数据接入与发布必须等待阶段 4 的环境确认。阶段 6 之后回到场景与反馈，以小版本继续迭代。

上述未来文档只在对应阶段创建；尚未存在的路径是明确的交付目标，不是当前代码证据。

## 任务流与任务卡

任务状态：`Idea → Ready → Doing → Review → User Check → Done`；遇到阻塞标注 `Blocked` 与解除条件，有新范围退回 `Idea`。

首版范围确认后，在 `docs/backlog.md` 用以下短模板管理，不要求外部工具：

```text
ID／标题：
状态／负责人：
用户场景与价值：
本次包含／明确不做：
验收条件（Given / When / Then，或可观察结果）：
受影响的现有文件／拟新增文件：
数据与权限影响：
验证命令／浏览器操作：
风险／回滚方式：
证据／用户反馈／未验证项：
```

### Ready：允许开工

- 用户确认该需求属于本次范围，输入、输出和验收条件明确。
- 所需 UI 状态／交互已确认，或者任务本身明确就是探索性原型。
- 依赖、目标环境、数据可见性和迁移影响已澄清；凭据与真实数据不是测试样例。
- 文件边界和可演示的终点明确；涉及额外成本、云资源或发布的授权已获得。

### Done：允许交付

- 需求验收逐条通过，未顺手加入范围外功能。
- `npm test`、`npm run lint`、`npm run build` 执行完成并记录结果；与基线相比不新增未解释的失败或警告。
- UI 变更在浏览器中验证主路径及相关状态，记录截图／操作结果；按影响覆盖明暗主题、键盘与目标屏宽。
- 数据变更在隔离环境验证保存／刷新／读取／权限；涉及编辑器时覆盖草稿恢复和原有回归。
- 差异检查完成，不带密钥、真实数据、意外锁文件改动或大范围无关格式化。
- 记录已知限制和回滚方式；用户体验确认后才标为 Done。未连后端的原型明确标注“样例数据”。

## Git 与上游策略

- 当前本地基础是 `origin/main`，初始化分支为 `codex/workstation-init`；来源提交记录在 `docs/baseline.md`。
- 远程镜像继续承担镜像还是兼作定制版仓库，留待讨论；不擅自创建新远程或改变镜像职责。
- 后续功能使用短生命周期分支、小提交；推送、合并和发布按用户授权执行。
- 保留上游来源、历史和说明，不在本轮重命名产品或调整许可声明。
- 同步上游时先比较差异，再在隔离分支验证定制逻辑、数据兼容与 UI 回归；不覆盖定制成果。

## 主要风险与处理

| 风险 | 已知依据 | 处理与验证 |
| --- | --- | --- |
| 误用原项目云环境 | `scripts/deploy-production.sh:4`、`.env.example:2`、`public/_worker.js:4` | 不执行现有部署命令；独立环境确认后检查所有地址、代理与资源名 |
| 按旧说明漏跑或误跑迁移 | `README.md` 的 Run locally 段、`supabase/migration-036-custom-avatar.sql:1`、`supabase/migration-010-cutover-drop-goal-model.sql:1` | 迁移准备时逐项比对目标库、当前文件和执行顺序；不将旧 README 当迁移账本 |
| UI 扩展破坏保存或隐私 | `ARCHITECTURE.md:22`、`ARCHITECTURE.md:169`、`test/resilientDocs.test.js:42` | 保留文档真源与读写权限边界；相关回归和跨用户访问测试纳入切片验收 |
