# 产品简报 · 讨论稿

状态：探索中。更新日期：2026-09-06。仅「已确认」部分代表用户明确表达的方向。

## 已确认

- 基于用户 GitHub 上的 `nownow-mirror` 做自己的定制版。
- 核心方向是效率工具，重点围绕 UI 界面展开。
- 面向个人或小团队，扩展更多个人任务管理能力。
- 先初始化，再逐步讨论；整个开发过程需要有流程、阶段产物和验收。
- 保留目前的记录、安排与跟进方式；当前优先改善编辑体验，而非另起一套任务管理流程。
- 编辑体验希望更顺滑，可参考 Apple Notes；“不是笔记本感”的具体含义先通过样稿验证，不直接解释成废弃文档模型。
- UI 希望适合长期工作，简约、现代、优雅，可带少量中国／日本古典气息，并探索有特点的中文字体。
- 用户希望先看 UI 风格样稿，再继续讨论。
- 定制产品不再沿用 `NowNow` 作为产品名；正式名称留待后续确定。讨论与样稿使用无品牌的“工作空间／工作文档”等功能称呼。
- 视觉中的古典字体需要被刻意看见，覆盖碑帖书法与古籍印刷质感，而不只是普通宋体标题。
- 不接受通用图标库直接套用于今日／本周／本月／收集箱；图形、符号和文字导航都必须能由产品哲学解释。
- 产品主体是可执行、可积累、可协作的工作文档；待办只是文档内容类型之一，不是产品全部。
- 中式色系和主要字体由同一显示设置管理，并提供多个可长期使用的选择；纸张质感退出当前范围，界面使用纯色表面。
- 传统色必须覆盖工作空间与纸面本身，不能只是白色界面中的强调色；色系数量需要继续扩展。
- 明体、宋体是主要阅读与编辑字体；书法字体不承担长文正文。
- 不显示“最后整理时间”一类编辑活动记录。
- 新一轮视觉希望在现有东方基础上继续做减法：从中正、典雅、大气转向日式侘寂、简约、纤细、略带虚无感。
- 时间范围的四个入口使用单字「日、周、月、元」；协作区只显示姓名，不加“与”等关系前缀。
- 显示设置不使用“主要字体”或“色”等分类标题：字体只显示明体／宋体，颜色以放大色块为主体、名称为小字注释。
- 产品正式采用名称「观复」，保留《道德经》“万物并作，吾以观复”作为品牌格言。
- 日／周／月属于当前文档写作模块的时间视图，放在正文顶部；左侧栏改为工作区、最近文档、项目与协作导航。
- 桌面端是主要构图基准，需要独立的桌面信息密度和宽度，不能沿用放大后的移动／平板比例。
- 日／周／月与插入／显示位于同一工具栏，减少文档顶部的层级占用。
- 编辑器输入 `/` 后出现 Markdown 功能组，可进入标题、待办、列表、引用、代码、分隔线、粗体等语法；正式实现需转换成 Tiptap 语义块而不只是插入字符。
- 显示设置支持独立修改正文字色，候选字色使用墨、朱砂、黛蓝、竹青、茶褐、梅紫等东方色系。
- “观复”标志采用红泥印章式长方块：浅色背景默认朱红底白字，背景色变化时印色自动协调。
- 印章颜色与背景方案一一固定，不提供单独修改 Logo 印色的设置。
- 左侧栏删除最近与项目；保留工作区、元、共作。
- 元是独立侧栏功能，记录不属于目标推进的信息；进入元后不显示日／周／月，也不使用目标型插入流程。
- 完整、顺滑、所见即所得的 Markdown 文档编辑体验是 P0、不可妥协的产品目标；未达成前不进入正式发布。
- Markdown 体验必须覆盖直接语法、语义化 Slash、粘贴／导入、导出往返、中文 IME、撤销、长文和可靠保存，不能等同于“插入语法字符”。
- 顶部不设置“插入”作为主要编辑方式；内容创建依赖自然书写、Markdown 快捷输入、Slash 与选区操作。
- 首个可用版本以个人长期工作为核心，保留现有 `@` 与成员查看能力但不扩展；小团队增强放在个人版稳定之后。

## 当前产品基础

源项目以按日／周／月／随手记组织的文档为核心，并提供团队 `@` 通知、编辑器待办勾选等能力。具体实现及证据见 [基线](baseline.md)。它为定制产品提供文档编辑与协作基础，但源项目名称不作为新产品名，也不代表独立个人任务管理模型已经存在。

## 工作假设（待用户确认）

- UI 调整应围绕高频任务组织和完成路径，而不只是换主题。
- 首个可体验版本只打通一个高频使用闭环；暂不同时承诺所有效率工具能力。
- 暂时复用现有技术栈，通过独立开发环境或隔离样例数据进行迭代。
- 对“不是笔记本感”的初步理解是减少拟物纸张、页框和反复进入编辑状态的阻力；待用户看过样稿确认。

## 讨论顺序

每轮一个关键问题，不要求一次填完需求表。

1. 还原典型一天：记录、安排、执行、跟进和回顾，找出一个最痛的场景。
2. 明确个人与小团队的优先关系，以及首版服务的设备和使用频率。
3. 决定任务与笔记的关系、基本状态及默认可见性。
4. 用上述场景选出 MVP 的必做、可延后与明确不做项。
5. 讨论信息架构、交互草图和视觉参考，确认一个可实现的方向。
6. 把范围拆成可演示的小切片，逐个开发与验收。

## Obsidian／Notion 借鉴结论

### 现在值得采用

| 来源 | 借鉴点 | 转化到本产品 |
| --- | --- | --- |
| Obsidian | Daily Notes 直接打开当天记录并可套模板 | 日／周／月一步进入持续工作文档；元独立收纳非目标信息，不增加文件夹选择 |
| Obsidian | 内部链接与反向链接帮助发现上下文 | 工作文档、项目、决定之间可链接；文末按需显示“被哪些文档提及” |
| Obsidian | 属性是小而原子的结构化信息，可隐藏 | 项目、日期、状态等元数据默认不占正文，只服务搜索与汇总 |
| Obsidian | 本地纯文本强调可携带与数据所有权 | 不立即重写现有存储；先加强可靠离线、Markdown／结构化导出与恢复能力 |
| Notion | 页面由可转换的多种内容块组成 | 在连续文档中明确行动、记录、决定、引用等语义块，可转换、移动和聚合 |
| Notion | 同一数据可通过筛选、排序和不同视图使用 | 从文档中的行动块自动生成轻量任务索引；不要求用户自己搭数据库 |
| Notion | 斜杠命令和键盘操作快速插入内容 | 收敛现有斜杠菜单，优先保证中文输入、键盘选择和块类型转换流畅 |
| Notion | 页面链接与协作反馈共存 | 沿用现有 @ 协作，后续再评估块级评论，不把通知等同于任务 |

### 明确不照搬

- 不做 Obsidian 式关系图谱、插件生态和大量个人配置入口。
- 不把当前产品改成本地 Markdown 文件夹；现有离线保存、版本历史、隐私与团队读取边界仍需保护。
- 不把 Notion 数据库、公式、看板、无限嵌套页面暴露为默认工作方式。
- 不让每条任务成为独立页面，也不做卡片式仪表盘；工作文档始终是主体。

当前建议模型：**文档是真源 → 内容块带轻量语义 → 链接形成上下文 → 任务与回顾视图由系统自动派生。**
